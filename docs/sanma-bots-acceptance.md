## 已复审并实际执行的发布屏障

发布检查不再把网页 API 的 `serviceRunning:false` 当作空牌桌证据。私有运维工具先核对容器 ID、3000 端口的唯一拥有者、Node/Next 命令、PID 和 `/proc` 启动时间，然后仅向该 Next 进程发送 SIGSTOP。麻将子进程继续运行，父 PID 仍然存活，牌桌内存保留。检查失败时只对同一容器、同一进程身份发送 SIGCONT；身份不明时保持维护入口关闭并要求人工恢复。

完整流程如下：

1. Caddy 暂时对整个网站返回 503，覆盖所有 URL 编码和路径形式。记录真实挂载文件的 inode，以及 Docker 配置路径经 `current` 解析的文件、将发布的文件；三者必须是同一份原始配置内容。屏障原地写入全部相关文件，因此每日备份重启 Caddy、切换 `current` 和回滚时仍有效。撤销前逐一核对 inode/本次写入的哈希，不能覆盖别人的修改。
2. 只暂停 Next，阻止旧请求的正文读取、鉴权回调、唤醒和转发继续执行。等待已转发的本机 3100 HTTP 请求完成；不把来自 Caddy 的非本机状态连接当作待排空命令；不通过暂停整个容器或麻将子进程来清空牌桌。
3. 检查当前数据库的其他客户端后端没有非闲置工作，最多等待 3 秒，仍有查询/事务就中止。这样即使 HTTP 客户端已断开，仍在等数据库的旧鉴权也不能被误判为空桌。随后要求麻将进程/监听端口确定不存在，或要求进程身份、内部健康响应及实例 ID 一致，并用本次短时会话逐个检查全部成员的内部牌桌。超时、未知身份和成员鉴权失败均中止；不跳过停用账号，也不撤销原会话。
4. 有牌桌或检查失败时恢复原 Next 和网关。确认空桌后保持 Next 暂停，直接停止旧应用，绝不先恢复它执行旧请求；然后制作新鲜一致备份。实际发布发现备份脚本恢复 Caddy 时，Compose 依赖关系重新启动了旧应用；整个站点入口屏障一直覆盖这段过程，屏障复核通过后才重建新应用。旧 Next 的积压请求随原进程停止丢弃，没有先 SIGCONT。新应用启动或回滚都在屏障内完成，健康检查通过后才恢复网关。
5. 临时维护可能使原 HTTP 请求返回 503，需要重试；Caddy 重载也可能让 WebSocket 重连。中止发布会保留真实牌桌，短时断线遵循原离线宽限。若进程或配置所有权变更、无法排空或无法恢复健康，不把失败当作可发布状态。
